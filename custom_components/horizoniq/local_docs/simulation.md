# Virtual-battery simulation core (Phase 2)

This package is pure Python and contains no Home Assistant imports or I/O. Energy is Wh, power is W and times are UTC. Grid import and battery charging are positive; export and battery discharge are negative. The 0.01 Wh default balance tolerance is floating-point accounting tolerance, not an unmodelled physical loss.

Phase 3 adds an isolated, per-entry runtime owner and virtual-battery device. A sandbox virtual battery is eligible only for a Sandbox registration with `virtual_battery` capacity source and a valid registration-owned equipment profile. Its read-only GX identity is `horizoniq-` plus the lower-case registration UUID without hyphens. Initial state is paused self-consumption at max(50% capacity, reserve), with zero synthetic load and solar; these are simulation defaults, not equipment measurements. The active-only **Set state of charge** number and `horizoniq.set_virtual_battery_state_of_charge` service set local stored energy to `capacityWh * percentage / 100` from reserve through 100%. They do not move virtual time or change equipment limits, reject profile playback/replay, and invalidate a prior direct command until the normal forecast cadence returns a new one.

Enable **Simulation** on the virtual-battery device to start that entry's clock and MQTT handlers. The clock-rate selector, **Step simulation**, and **Reset simulation** controls operate only on that device; disabling it stops its handlers and returns its cloud coordinator to normal polling. Operational sensors are unavailable while disabled, while the status sensor remains visible.

The integration uses Home Assistant's configured MQTT connection. Configure a sandbox-only broker account for Node-RED, and restrict it to generated `victron/N/horizoniq-*`, `victron/W/horizoniq-*`, `victron/R/horizoniq-*`, and `horizoniq/sandbox/horizoniq-*` prefixes where broker ACLs support this. No sandbox topic can be constructed from a production GX ID.

MQTT support uses Home Assistant's required `mqtt` integration and only generated sandbox GX IDs. While enabled, a runtime subscribes to exactly three frozen Victron `W` topics, one `R` keepalive, canonical `commands/issued`, and its replay-status topic. Retained `W`, `R`, and issued-command messages are ignored before parsing. Setup failure rolls back only the owning entry and resumes only its coordinator; inactive or unloaded runtimes ignore late callbacks.

## Frozen Victron telemetry and refresh contract (Phase 4 Step 18C1-HA2)

Every synthetic snapshot publishes these eight non-retained `{"value": number}` notifications under `victron/N/horizoniq-<32 lowercase hex>/`: `battery/512/Soc` (percent), `battery/512/InstalledCapacity` (Ah), `battery/Power` (W), `grid/Power` (W), `system/Load` (W), `solar/Power` (W), `battery/Voltage` (V), and `system/OperatingState` (0 idle, 1 self-consumption, 2 grid setpoint). Installed capacity is the registration-owned configured Wh divided by the registration-owned nominal voltage; the sandbox default is 48 V. Stored energy remains a separate local simulator value and is not republished as installed capacity.

The exact non-retained write subscriptions are `settings/0/Settings/CGwacs/Hub4Mode`, `vebus/274/Mode`, and `settings/0/Settings/CGwacs/AcPowerSetPoint`. The sole refresh subscription is `victron/R/horizoniq-<32 lowercase hex>/keepalive`; it accepts only an empty payload or `{}` and republishes that runtime's complete current N snapshot without advancing physics or changing command state. Initial enable, simulation steps/profile playback, applied writes, and resets use the same snapshot builder and entry-local fault-aware outbound bridge.

## Frozen command lifecycle (Phase 4 Step 18C2-HA3)

The only command metadata input is non-retained `horizoniq/sandbox/horizoniq-<32 lowercase hex>/commands/issued`; the only HA response is the matching `/commands/status`. The former `commands/intent` and `commands/ack` topics have no aliases and are not subscribed or published.

Issued metadata is strict schema 4 with matching generated GX, plan/command UUIDs, a supported action, explicit-`Z` issued/effective/expiry timestamps, and expected Hub4, VE.Bus, and AC-setpoint values. A valid current command publishes `received`, then remains local and inert until all three exact non-retained `W` values arrive. It then applies atomically and publishes `applied`. Mismatch, expiry, timeout, disable, unload, or disconnect returns to self-consumption and publishes `rejected`, `expired`, or `failed` while MQTT is still available. Each status is non-retained schema 4 with matching identity, virtual-UTC `Z` timestamp, bounded reason, and local synthetic SoC/battery/grid/operating-state summary.

At most one command is pending per entry. Accepted command IDs are retained in that entry's private Store for 86,400 virtual seconds, capped at 1,024 IDs, and contain only ID plus accepted virtual timestamp. Neither issued metadata nor individual `W` values are stored. Schema 6 introduced the ledger; schema 7 added replay-failure state; Store schema 9 and snapshot schema 2 retain the current migration-safe state. Named snapshots never reset duplicate protection or resume a partial command. `reject_command` runs only after valid issued metadata and before `received`; transport faults use the existing outbound precedence.

## Persisted simulator state (Step 17A)

Each eligible sandbox has one private Home Assistant storage record, keyed by its config-entry ID and checked against its canonical registration and generated GX identities. Store schema 9 writes snapshot schema 2, which preserves synthetic inputs, editable control values, profile/playback identity, replay metadata, command state, and fault definitions needed for deterministic local reproduction. Schema-1 snapshots and Store schema 8 remain readable with safe local defaults. It never contains HorizonIQ credentials, broker settings, production identities, forecast payloads, actual telemetry, or observed command outcomes.

Checkpoints are debounced to at most one write per 30 real seconds during simulation, with immediate saves after lifecycle actions, explicit steps, and manual state-of-charge changes. A signed `manual_adjustment_wh` local ledger term accounts for setup energy without treating it as grid, solar, loss, saving, actuals, or telemetry. A clean unload flushes state; deleting the config entry removes only its own simulator record. An invalid, incompatible, or mismatched stored record remains untouched and the sandbox starts disabled with a local diagnostic. Restoring a snapshot validates before commit, preserves the duplicate-command ledger, clears obsolete callbacks/queues, and recreates only the restored entry's active fault effects; it does not call the forecast backend.

## Local synthetic profiles (Step 17B1)

Profiles are read only from `<HA config>/horizoniq/profiles/<config_entry_id>/`. Each file must be a direct UTF-8 `.json` or `.csv` child of that entry's directory and no larger than 4 MiB. Paths outside that directory, absolute paths, traversal, and unsupported extensions are rejected.

JSON uses `{ "schema_version": 1, "name": "optional", "starting_battery_energy_wh": 5000, "samples": [...] }`. Each sample has exactly `timestamp`, `load_w`, `solar_w`, `import_rate_gbp_per_kwh`, and `export_rate_gbp_per_kwh`. CSV has those same five columns as its exact header and has no metadata row. Timestamps require an explicit offset; profiles contain contiguous five-minute samples, begin and finish on half-hour boundaries, contain a multiple of six samples, and are limited to 31 days/8,928 samples.

Selecting a profile validates it before changing sandbox state. Local playback advances only from the virtual clock and splits each simulation update at five-minute boundaries. The Store keeps only the selected filename, SHA-256 content hash, cursor, and playback state—not the profile content. A missing or changed file pauses restore with a local diagnostic. Step 17B1 does not request Node-RED replay, publish profile data, or call the forecast backend.

## Replay contracts (Step 17B2A)

Step 17B2A adds pure, unconnected contracts only; it does not publish MQTT, alter playback, call Node-RED, or persist a replay session. Six validated five-minute samples become one half-hour period with summed load/solar kWh and time-averaged import/export prices. A future replay request is schema version 1 with `replayId`, `effectiveAtUtc`, `startingBatteryEnergyKwh`, `importForExportEnabled`, `exportForSolarHeadroom`, and contiguous `periods`; every time is explicit UTC `Z`. It is limited to 1,488 half-hour periods and 1 MiB. It cannot contain registration IDs, credentials, production identities, actual telemetry, commands, outcomes, or override fields.

The local request hash is SHA-256 over canonical JSON and is only an HA-local duplicate/restore guard; it is not claimed to match JavaScript byte-for-byte. A replay ID may not identify different local request content. The versioned, not-yet-stored session value has only the replay ID/hash, local lifecycle state, clock sequence, accepted remote status/reason, and selected profile identifier/hash.

Future bridge topics are fixed to `horizoniq/sandbox/horizoniq-<32 lowercase hex>/replay/request`, `/replay/status`, and `/clock/status`; no other GX shape is accepted. Remote status is strict schema 4 (`gxDeviceId`, `replayId`, `state`, `reason`) and accepts only `loading`, `ready`, `rejected`, or `failed` for the owning active request. Local transitions are `idle → requesting → loading → ready`, then `running`, `paused`, or `completed`; only legal in-order statuses can change state, and an active replay may become `stopped`.

Clock status is also schema 4 and contains only `gxDeviceId`, `replayId`, `virtualTimeUtc`, `sequence`, and `reset`. A reset is sequence zero; later heartbeats increment strictly, may retain virtual time while paused, and cannot move virtual time backward unless reset. Completion is represented by the local replay state, not an executable command. MQTT/runtime orchestration remains Step 17B2B.

## Replay request lifecycle (Step 17B2B1)

Step 17B2B1 connects only the request/status lifecycle. An enabled, eligible sandbox with a selected unchanged profile can prepare and publish one schema-1 replay request. It uses the profile’s half-hour aggregates, profile starting energy (or the virtual battery’s current energy), and registration-owned `ImportForExport` / `ExportForSolarHeadroom` booleans. Missing booleans are `false`; non-boolean values reject the start. Callers cannot supply request fields or override those values.

The runtime subscribes only to `horizoniq/sandbox/horizoniq-<32 lowercase hex>/replay/status` and publishes only to its corresponding `/replay/request` topic, with `retain=false`. It never calls a replay HTTP/backend endpoint. A request is published once per explicit session; duplicate starts while requesting/loading/ready are rejected. Matching, in-order schema-4 statuses can move the local session through loading, ready, rejected, or failed. Ready deliberately does not start playback and does not publish clock messages.

After a successful request publication, the owning entry has a 30-real-second readiness timeout. Terminal statuses, disable, stop, unload, and removal cancel it without affecting another entry. Store schema 9 persists only replay-session value metadata, starting energy, trusted toggle snapshot, pending-resume state, and the boolean needed to reconstruct a pending `simulateApiFailure` request. A restart revalidates and rebuilds the profile request with the saved replay ID/hash; B2B2 republishes that request once only after the owning MQTT setup succeeds. Full profile content, request horizons, MQTT settings, secrets, actual telemetry, outcomes, and backend response plans are not stored.

## Replay playback and clock bridge (Step 17B2B2)

On the single valid in-order `ready` status, the owning sandbox revalidates its selected profile/hash, initializes the request’s validated starting energy, starts local five-minute playback, and emits one non-retained schema-4 reset message on `horizoniq/sandbox/horizoniq-<32 lowercase hex>/clock/status`. No Node-RED plan, action, advice, command, actual, or replay result is received or stored. Existing sandbox Victron `W` writes remain the only command-authoritative input; profile prices are never treated as commands.

Clock messages use the virtual clock only. Reset is sequence zero; later messages strictly increase the session sequence and cannot move virtual time backward without reset. Messages are rate-limited to one per real second, sent for reset, explicit virtual steps, half-hour crossings, pause/resume, completion, and at least every 30 real seconds while running or paused. A paused heartbeat leaves virtual time unchanged. Disable/unload cancels all timeout/heartbeat work and prevents further publication.

Natural completion clears inputs and returns to safe self-consumption after publishing the terminal out-of-horizon clock position. Explicit stop does the same without inventing a cancel topic. A failed clock publication fails only that replay and stops its local playback. Store schema 9 distinguishes an ordinary restart-resume request from a named-snapshot restore: a restart republishes the same validated request ID/hash once after MQTT setup and waits for `ready`; snapshot restore remains stopped/pending and never republishes automatically.

An active `replay_api_failure` fault consumes one occurrence while HA forms an otherwise valid replay request, adds only `simulateApiFailure: true`, and publishes through the normal non-retained sandbox outbound bridge. HA waits for the matching Node-RED schema-4 `failed` status with reason `simulated_api_failure`; it does not fail locally, publish a clock reset, start playback, call a backend, or change the battery. This models Node-RED's frozen simulated failure path only; real backend failure injection remains outside HA. Transport disconnect, drop, and delay faults still apply after the flagged request is formed.

HA publishes non-retained schema-2 simulator and fault summaries on its generated-GX `simulator/status` and `faults/status` topics. Simulator status has typed synthetic battery, clock, health, MQTT, replay, and command fields; fault status has only bounded fault kind, lifecycle, and remaining counter/duration fields. Diagnostic `reason` is nullable plain text only and never encodes values, JSON, credentials, backend responses, plans, actual telemetry, outcomes, or delayed MQTT data. Node-RED's exact non-retained schema-1 `node-red/status` envelope remains memory-only and is rejected when stale, malformed, retained, or for another generated GX ID.

## Fault model (Step 17C1)

Step 17C1 stores a pure, deterministic fault model only. The eight supported kinds are `stale_telemetry`, `drop_mqtt`, `delay_mqtt`, `malformed_telemetry`, `replay_api_failure`, `reject_command`, `mqtt_disconnect`, and `runtime_restart`. Each entry allows at most 16 faults and at most one non-cleared fault of any kind. Counts are bounded to 1–100 (10 for malformed telemetry and runtime restart); timed faults are 1–900 seconds; MQTT delay is 0.1–60 seconds. Reasons are bounded to 256 characters.

The future outbound precedence is disconnect, drop, delay, malformed telemetry, then normal publication. Command, replay, telemetry, and restart kinds are separately scoped to their owning sandbox. In C1 none of these definitions is connected to MQTT, commands, replay, tasks, physics, or the backend. Store schema 5 and named snapshots retain only validated fault state/counters/durations; no queued messages, exception objects, secrets, production identifiers, actuals, or outcomes are stored.

## Outbound fault effects (Step 17C2A)

Step 17C2A applies only entry-local outbound effects. `stale_telemetry` suppresses synthetic Victron `N` publication without replaying old values. `drop_mqtt` consumes and drops the next generated-sandbox outbound messages. `delay_mqtt` queues generated-sandbox outbound messages in FIFO order, up to 100 in memory only, then publishes them after its validated fixed delay. `malformed_telemetry` consumes one event and substitutes the fixed `{"value":["invalid"]}` representation only for synthetic `N` telemetry. `mqtt_disconnect` removes only that runtime's subscriptions, suppresses its publications, puts its local command state into self-consumption, and reconnects only that enabled runtime after expiry.

The precedence is disconnect, drop, delay, malformed telemetry, normal publication. Queues and scheduled work are discarded on disable/unload; no queued payload is persisted. `replay_api_failure`, `reject_command`, and `runtime_restart` remain effect-free until Step 17C2B. No backend HTTP call is added.

## Remaining fault effects (Step 17C2B)

`replay_api_failure` consumes only when HorizonIQ is about to publish a validated replay request, suppresses that request, and moves the owning local replay session to failed with a deterministic diagnostic. It does not make or fabricate an HTTP call or malformed request. This models the HA-visible consequence only; true Node-RED/backend failure injection remains Phase 4 work. Retry uses the existing new replay ID and can succeed after the fault is exhausted or cleared.

`reject_command` applies only after canonical issued metadata is otherwise valid. It retains the prior local command/battery state, consumes one occurrence, and sends the canonical rejected command status through the same outbound bridge. `runtime_restart` consumes and checkpoints its own occurrence before stopping and restoring only the owning runtime through its Store path. It never restarts Home Assistant, Python, the broker, or another config entry. No user-facing fault controls are provided.

## Phase 5 operational controls and setup

The virtual-battery device exposes normal Home Assistant controls only. The **Simulation** switch remains visible while configured. When it is on, manual number entities set synthetic load, solar, capacity, reserve, charge/discharge limits, and charge/discharge efficiency; selectors set clock rate, scenario, validated replay profile, the registration-owned equipment profile label, and a fault kind. Load and solar are 0–100,000 W; capacity is greater than zero and at most 2,000,000 Wh; reserve is 0–2,000,000 Wh and cannot exceed capacity; charge/discharge limits are 0–100,000 W; efficiency is greater than zero and at most 100%. Buttons step/reset the clock, reset a profile, save a local snapshot, inject the selected bounded fault, and clear faults. All operational entities become unavailable when the switch is off.

Use the `horizoniq` integration services for actions requiring input or a result: profile load/start/pause/stop/reset, `step`, `reset`, snapshot create/list/restore/delete, and fault configure/activate/clear. Services require the matching config-entry ID and cannot target a Live entry. A snapshot is entry-local; it records virtual state, virtual time, profile cursor, command state, ledger, and faults. It does not record MQTT credentials, actual telemetry, forecast plans, or production identifiers.

The energy ledger is a modeled conservation check: grid import + solar + battery discharge must equal load + battery charge + grid export + modeled conversion losses. `Energy-balance health` becomes unhealthy when the measured balance error exceeds the configured numerical tolerance. A non-zero loss is expected with less-than-100% efficiency; a balance error is not a financial value.

For one-time broker setup, configure Home Assistant's MQTT integration with Mosquitto or another compatible broker, create one sandbox-only account for Node-RED, and apply ACLs for `victron/[NWR]/horizoniq-*` and `horizoniq/sandbox/horizoniq-*`. Each Node-RED sandbox has a unique client ID and the generated GX ID for exactly one HorizonIQ Sandbox entry. Enable a sandbox, verify the MQTT health sensor, step it, confirm `N` telemetry and matching non-retained `W` command acknowledgement, then send the generated `R/.../keepalive` request. Repeat with another Sandbox to prove topic isolation. Topics are automatic: do not provision them manually.

See `examples/lovelace-sandbox.yaml` in the integration repository for a conditional dashboard section. Copy it once per sandbox and replace the entity IDs from your own installation; a custom card or automatic dashboard modification is intentionally not used.
